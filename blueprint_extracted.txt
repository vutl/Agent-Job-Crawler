AI JOB INTELLIGENCE
Complete Project Blueprint
Crawl public job postings → extract skills → analyze market demand → generate learning roadmaps → deploy as a production-style web system
Primary learning stack: Python · FastAPI · PostgreSQL · Redis · LLM routing · Next.js · Docker · Jenkins · Kubernetes · AWS · Argo CD · Prometheus/Grafana
Version 1.0 — August 2026
1. Project Goal
Build a production-style AI Job Intelligence platform that continuously collects public job postings, normalizes job descriptions, extracts explicit skill requirements, aggregates market demand by role, and displays the results in a web dashboard. The system should also generate evidence-based learning roadmaps for roles such as AI Engineer, ML Engineer, MLOps Engineer, Data Scientist, and Backend/Platform Engineer.
What makes this project valuable
Real data pipeline: you are not building a toy chatbot; you are ingesting, processing, storing, analyzing, and serving changing external data.
Clear AI boundary: deterministic code handles crawling, parsing, deduplication, persistence, and statistics; LLMs handle semantic extraction, classification, normalization, and summarization.
Natural DevOps use case: crawler workers, API, frontend, scheduled jobs, queues, databases, CI/CD and observability all have legitimate reasons to exist.
Strong portfolio story: the final product demonstrates AI engineering, backend engineering, data engineering, cloud deployment, and production operations in one coherent system.
Non-goal for V1
Do not attempt to become a general-purpose job board, application tracker, resume optimizer, or LinkedIn competitor. V1 focuses only on job-market intelligence and learning recommendations.

4. How to Use colophon-group/jobseek
Use Jobseek as a reference implementation and selective crawler donor, not as the full product base. Its current repository already contains a mature Python crawler, async workers, Redis queues, Postgres, Typesense, a Next.js application, monitor/scraper abstractions, Playwright fallback, labelling workflows, and significant production operations. Forking the entire system would hide many of the infrastructure lessons this project is intended to teach.
Reuse / study
Monitor abstraction for ATS systems such as Greenhouse, Lever, Workday and similar career platforms.
Scraper abstraction: structured JSON/JSON-LD first, DOM parsing second, browser fallback last.
Async crawling patterns, retries, rescheduling and queue semantics.
Canonicalization and deduplication strategies.
Job-posting field normalization and crawler test patterns.
Board/company configuration patterns.
Do not bring into V1 unless needed
Application tracker, watchlists and authentication.
Full Typesense architecture, multi-language UI, SEO systems and notification products.
Their complete ops/automation stack.
Any component you cannot yet explain in one or two sentences.
License note
Jobseek states that its code is MIT licensed, while its included job-posting data is separately licensed under CC BY-NC 4.0. Treat code reuse and data reuse as separate decisions, preserve required notices, and do not assume the dataset license is identical to the source-code license.

Important data principles
Keep raw evidence: save the raw/normalized description and the exact text span supporting each extracted skill.
Version AI outputs: store model name, prompt version and extractor version so you can reproduce and compare results.
Do not overwrite history blindly: use first_seen_at, last_seen_at, status and snapshots for trends.
Deduplicate before analysis: avoid paying an LLM twice for the same unchanged posting.
6. Crawler Strategy
Source priority
Official structured endpoints first. If a company uses a known ATS with a public JSON endpoint, prefer it.
Static/SSR HTML second. Use httpx/requests + BeautifulSoup/lxml.
Embedded JSON / JSON-LD third. Often cleaner than rendered DOM.
Playwright only when necessary. Use browser crawling for JavaScript-rendered pages that cannot be accessed reliably otherwise.
Crawler constraints
Only access publicly available pages/endpoints you are permitted to access.
Do not bypass CAPTCHA, login gates, authentication, paywalls or anti-bot controls.
Respect reasonable request rates and source-specific terms/policies.
Track source failures separately from “zero jobs found” to avoid silent data loss.
Add timeouts, retry with backoff, and per-domain concurrency limits.
Crawler workflow
discover board -> enqueue source -> fetch -> parse -> validate -> canonicalize-> hash content -> upsert job -> mark changed/new -> enqueue analysis
7. AI / Agent Layer
The core AI component should be a structured extraction pipeline, not a free-form autonomous agent. An agent can later orchestrate analysis and answer user questions, but the ingestion path should remain predictable.
Extraction schema
{  "role_family": "AI Engineer",  "seniority": "mid",  "skills": [    {      "name": "Kubernetes",      "category": "devops",      "requirement_type": "required",      "evidence": "Experience deploying services on Kubernetes...",      "confidence": 0.97    }  ],  "years_experience_min": 3,  "education_requirement": "bachelor_or_equivalent"}
LLM provider abstraction
Do not couple the application to a single provider. Implement an OpenAI-compatible adapter with configuration for base URL, API key and model. This makes it straightforward to use a router such as 9router if its current API exposes an OpenAI-compatible interface, and it also lets you swap to OpenAI, another gateway, or a local model without rewriting business logic.

8. Analytics and Product Logic
Metrics to compute deterministically
Percentage of active postings for a role mentioning each skill.
Required vs preferred frequency.
Skill frequency by seniority, country, company size/source, and time window.
Fastest-growing / declining skills using weekly or monthly snapshots.
Common skill pairs: e.g., PyTorch + CUDA, Kubernetes + Docker, AWS + Terraform.
Role overlap: skills shared between AI Engineer, ML Engineer and MLOps Engineer.
Roadmap generation rule
The LLM must receive aggregated statistics and a constrained set of observed skills. It should not invent fashionable technologies that are absent from the evidence window. Every generated roadmap should state the number of jobs, selected time window and geography/filter used.

13. Observability
Application metrics: jobs discovered, jobs changed, crawl success rate, parser failures, queue depth, analysis throughput.
LLM metrics: requests, latency, token usage, cost estimate, validation failures, escalation rate.
Data quality: percentage of jobs missing descriptions, duplicate rate, stale-source count, extraction confidence distribution.
Infra metrics: CPU/memory, pod restarts, HTTP latency/error rate, DB pool saturation.
Logs: structured JSON with source_id/job_id/request_id so a bad record can be traced across services.
Add Prometheus + Grafana after the application runs end-to-end. Create at least one useful dashboard and one alert, for example: “crawler source failure rate > 30% for 30 minutes” or “analysis queue oldest item > 1 hour.”

18. Portfolio / Interview Story
A strong final explanation should sound like engineering decisions, not a list of tools:
“I built a job-market intelligence platform that monitors public company career pages, normalizes and deduplicates postings, uses structured LLM extraction to identify required technologies, and computes time-series demand by engineering role. I separated deterministic ingestion from semantic analysis for reliability and cost control. The system runs as containerized workers and services, uses CI for PR validation, publishes images to a registry, and is deployed to Kubernetes through GitOps. I also built a golden evaluation set to compare extraction models and routing strategies.”

20. Recommended Principle
Build the product first, then earn each infrastructure tool. Docker should solve reproducibility, Jenkins should solve automated validation, Kubernetes should solve multi-service scheduling and lifecycle management, AWS should solve hosting, Argo CD should solve deployment-state management, and observability should solve operational uncertainty. If a tool is present only because it looks good on a stack list, delay it until the system creates a real need for it.
